CODE PURPLE architecture / ownership & control signals

Forward DAG + separate control overlay | V3.2

The previous purple filled boxes were decorative, not proof of ownership, completion or phase. Phase is numbered, responsibility is written on the node, state is explicit, and branch decisions use opposite meaning and color.

Visual grammar / legend

Activity / process (neutral fill) Decision (diamond) Owner is a role label, not fill YES / eligible path (green) NO / HOLD (red) Forward dependency (DAG) Feedback, dashed amber / next pulse Feedforward, double cyan / preflight

Green/red branch outlines and labels encode conditional dispositions, not observed governance approval. Purple borders identify a decision type only; no single global owner is implied.

Roles are distributed; one root has one accountable repair owner

Source producers

GitHub Actions / scanners / Docker / RHEL / LLDB. Responsibility: emit source-bound native receipts.

Control-plane ledger

ABACUS EVERRED. Responsibility: stable root identifiers, immutable evidence and deterministic joins.

Dispatch & triage

Mission Control / REX. Responsibility: diagnose, classify and assign; actual named operator: UNKNOWN until authenticated.

Bounded repair

One canonical root owner per confirmed root. Disjoint source paths and leased scope; not ownership of entire programme.

Technical verification

Trusted SUT/CI runners and gg_MATH provider. Local previews never replace exact-head native evidence.

Independent admission

Effective repository policy + eligible independent reviewers; separate from tool authors and executing workers.

Purple branding has no semantic operational meaning. No universal single owner, and no phase is inferred from color. Each role is a contract, not evidence of a live assigned person.

2. Feedback and feedforward (separate control graph, NOT part of the DAG)

FEEDBACK ← corrective learning (amber dashed)

Observed first-red, new root signature or regression triggers a new causal investigation. This creates a cycle only across iterations; it cannot be drawn as an edge inside a strict DAG.

FEEDFORWARD → predictive preflight (cyan double)

Earlier fingerprint recurrence or risk estimates inform which tests to stage before expensive CI. This is a proposed control strategy, not evidence that a forecasting worker is currently operating.
