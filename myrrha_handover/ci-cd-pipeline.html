Stage 2: Version Control (Git)

Repository Initialization

# Initialize Git repo cd /home/ubuntu/myrrha_handover/ git init git remote add origin https://github.com/[USER]/myrrha-wcs-handover.git # Initial commit git add -A git commit -m "feat: initial v0.4.2 release — full WCS handover ecosystem" git tag -a v0.4.2 -m "v0.4.2: severity rankings, vendor scouts, CI/CD" git push -u origin main --tags

Branch Strategy

main ─────●────────●────────●────── (production stable) \ / develop ─────●──●──●──●──●──────── (active development) \ / feature/* ───────●──●────────────── (feature branches) Branches: main → production stable (protected, PR-only merges) develop → active development (daily work) feature/* → feature branches (e.g., feature/vendor-scout-mt11) hotfix/* → emergency fixes (merge to main + develop)

Stage 3: GitHub Actions CI

.github/workflows/ci.yml

name: CI - Build and Test on: [push, pull_request] jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v3 - name: Setup Python uses: actions/setup-python@v4 with: python-version: '3.10' - name: Install dependencies run: pip install -r requirements.txt - name: Run rendering pipeline run: python3 master/render_all.py - name: Validate HTML run: python3 tests/validate_html.py - name: Run QA checks run: python3 tests/qa_suite.py - name: Check data.json schema run: python3 tests/validate_data.py - name: Upload artifacts uses: actions/upload-artifact@v3 with: name: rendered-html path: ./*.html

Stage 4: GitHub Pages Deployment

.github/workflows/deploy.yml

name: CD - Deploy to GitHub Pages on: push: branches: [main] permissions: contents: read pages: write id-token: write jobs: deploy: runs-on: ubuntu-latest environment: name: github-pages steps: - uses: actions/checkout@v3 - name: Setup Python uses: actions/setup-python@v4 with: python-version: '3.10' - name: Build site run: python3 master/render_all.py - name: Deploy to GitHub Pages uses: peaceiris/actions-gh-pages@v3 with: github_token: ${{ secrets.GITHUB_TOKEN }} publish_dir: ./ cname: myrrha-wcs.engineering.example.com

Stage 5: Authentication Strategy

Option A: Development Bypass (Quick Access) ★

Simple session-based auth gate for development/internal sharing. No server required.

// Add to index.html <head> — Development quick-pass // Prompts for credentials on first visit, stores in sessionStorage (function() { const DEV_USERS = { 'admin': 'admin', 'dev': 'dev123', 'engineer': 'myrrha2026' }; if (!sessionStorage.getItem('myrrha_auth')) { const user = prompt('MYRRHA WCS — Username:'); const pass = prompt('Password:'); if (DEV_USERS[user] === pass) { sessionStorage.setItem('myrrha_auth', 'true'); sessionStorage.setItem('myrrha_user', user); } else { alert('Access denied. Contact engineering team.'); document.body.innerHTML = ''; window.location = 'about:blank'; } } })();
UsernamePasswordRole
adminadminFull access
devdev123Developer
engineermyrrha2026Engineering team

⚠ Not for production — credentials in client JS. Suitable for internal dev/review access only.

Option B: GitHub Pages + Cloudflare Access

Enterprise-grade zero-trust access via Cloudflare. SSO integration.

1️⃣
Deploy to GitHub Pages (public repo, or org-level private pages)
2️⃣
Add Cloudflare DNS in front of GitHub Pages
3️⃣
Configure Cloudflare Access application for the domain
4️⃣
Set access policy: allow specific email domains (e.g., @sckcen.be, @myrrha.eu)
5️⃣
Enable SSO via Google Workspace or Microsoft Entra ID

✓ Server-side auth · ✓ SSO · ✓ Audit logs · ✓ IP restrictions · Cost: Cloudflare Zero Trust free tier (50 users)

Option C: Private GitHub Repo

Rely on GitHub's built-in authentication. Simplest setup.

1️⃣
Keep repository private
2️⃣
Enable GitHub Pages for private repo (requires GitHub Pro/Team/Enterprise)
3️⃣
Add collaborators via GitHub team management
4️⃣
GitHub Pages serves only to authenticated collaborators

✓ Zero config · ✓ Native GitHub auth · ✗ No SSO · ✗ Requires GitHub account · Cost: GitHub Team ($4/user/mo)
