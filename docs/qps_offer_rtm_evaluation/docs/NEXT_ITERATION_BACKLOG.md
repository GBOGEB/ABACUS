## 10. BT win % / BT λ index / Pearson question -- resolved with real numbers

GBO asked for sample hand-calcs of Weighted S, BT win %, and a "normalized
ratio," plus asked about a Pearson value "around 0.99" and "~350 iterations
to stabilize." Checked directly against the live workbook rather than
assumed:

**Weighted S -- confirmed formula, hand-verified**: `S = 100 x (sum of each
of the 7 raw 0-3 dimension scores x its frozen weight) / 3`. Frozen weights
(WEIGHTS_METHOD sheet): Safety/Legal 0.20, Reliability 0.22, Performance
0.20, Functional 0.16, Quality/Verifiability 0.12, Lifecycle 0.07, Cost
0.03. Worked example, RTM-693 (rank #1): raw scores L=3, R=2, P=0, F=3,
Q=3, LC=0, C=0 -> weighted sum = 3(.20)+2(.22)+0(.20)+3(.16)+3(.12)+0(.07)+0(.03)
= 1.88 -> S = 100 x 1.88 / 3 = **62.67**, matching the workbook exactly.

**BT win % -- confirmed formula, NOT iterative**: `winPct = 100 x (N - rank)
/ (N - 1)` where N=722, a pure linear transform of rank position (ties get
an averaged/fractional effective rank). Verified exactly against multiple
rows (rank 1 -> 100.00, rank 2 -> 99.86, rank 101 -> 86.13, all match the
stored value to 4 decimals). This is a **static, one-time, deterministic**
calculation -- there is no iterative fitting process anywhere in this
project's BT win % computation, and therefore no "~350 iterations to
stabilize" happening for this metric. Pearson(rank, winPct) = -0.998 (near
-1, as expected for an almost-exactly-linear transform).

**BT λ index -- a real third metric, currently NOT exported to the
Navigator (found this round)**: RTM_RANKING col X / OFFER_RANKING col Q,
labelled "BT λ index," described in WEIGHTS_METHOD as useful "only for
relative separation... not X% vs Y% compliance." Unlike win %, λ decays
much faster than linearly with rank -- roughly exponentially:
Pearson(rank, log(λ)) = **-0.9965**, close to the "~0.99" GBO recalled.
This is the metric that most resembles a genuine Bradley-Terry fitted
relative-strength parameter. However: **no build script in this repo
computes λ** -- like several other columns, it predates
`build_workbook_full_v5.py` (inherited from the original hand-edited
baseline / `QPS_RTM_BT_Standalone.xlsx` merge). I could not find or
reconstruct an iterative-fitting process anywhere in this codebase, so I
can't confirm or deny the "~350 iterations" recollection -- if that
computation happened, it happened outside what's inspectable in this
repo. Flagging as a real open question rather than guessing either way.
**Action for next iteration**: (1) add `btLambda` to `export_nav_data.py`
and surface it in the Navigator (currently invisible there entirely);
(2) ask GBO directly whether he has the original λ-fitting method/script
from wherever the baseline workbook came from -- that would resolve the
iteration-count question definitively instead of reverse-engineering it
from output values alone.

## Section 25 — PCA-clustered Pareto analysis for the P1 cutoff (task #58) -- done, real finding, does NOT replace the flat-rank Pareto answer

Direct response to: "yes data driven BUT already knowledge and process --
rather try the PCA to group the relevant pareto?" Ran `pca_pareto_cluster.py`
against all 722 RTMs' standardized 7-dimension (L/R/P/F/Q/LC/C) scores.

Two different questions, kept explicitly separate (conflating them was the
risk flagged in Section 19-adjacent notes):
1. Existing PCA (PC1=30.6%, PC2=16.5% var) -- how correlated the 7 scoring
   DIMENSIONS are with each other (a variable-space question).
2. This analysis -- cluster the 722 RTM ITEMS in that PC-space and check
   whether a natural item grouping produces a cleaner "critical few" cutoff
   than the flat Sum-Weighted-S ranking already debunked in Section 19.

KMeans silhouette scan (k=2..6) on standardized raw scores picked k=5
(silhouette=0.353, mildly better than k=4's 0.339). The 5 clusters that
fall out are **requirement-TYPE clusters, not importance-tier clusters**:
- Cluster 2 (highest mean weighted-S, 1.343): n=105 (14.5%), dominant dim
  R (Reliability, mean 2.78) -- reliability-heavy requirements.
- Cluster 4: n=15 (2.1%), dominant dim C (Cost, mean 2.80) -- cost-driven
  items.
- Cluster 0: n=159 (22%), dominant dim Q (Quality/Verifiability).
- Cluster 3: n=78 (10.8%), dominant dim LC (Lifecycle).
- Cluster 1 (largest, 50.6%): dominant dim F (Functional), lowest mean
  weighted-S (0.746).

Critically: the highest-scoring cluster (Cluster 2) spans **rank 10 to
561** -- i.e. it is NOT a contiguous top tier. Cross-checked against a
flat top-105-by-rank slice: only 38/105 (36%) overlap. The existing
administrative top-36 (5%) cutoff is split across all 5 clusters (9/2/19/
4/2), landing mostly but not exclusively in the Reliability-dominant
cluster.

**Honest conclusion**: PCA-based item clustering answers "what natural
requirement TYPES exist" (useful for reviewer specialisation -- e.g. route
Cluster 2 to your reliability engineers, Cluster 4 to procurement/cost
reviewers), not "where does importance naturally break." It does NOT
produce a cleaner data-driven P1 threshold than the two already-offered
honest options (an 80%-of-importance line at rank ~490, or keep the
administrative top-N relabelled as a workload cutoff, not an importance
claim). This is a genuinely different, useful cut of the data (buildable as
a "review by requirement type" view in the Navigator/deck) -- but it should
be presented as that, not as a replacement Pareto threshold.

Output: `/tmp/pca_cluster_results.json` (full profiles, loadings,
silhouette scores) -- not yet wired into any deliverable; candidate content
for task #59's deck update or a new Navigator panel.
